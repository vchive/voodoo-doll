# 0008 · TypeScript 统一与无服务化边界

日期：2026-09-19（Asia/Shanghai）
状态：**架构决策；本地单机模式可选，线上世界仍由服务端承载**

## 背景

项目可以把前端和后端都写成 TypeScript，也可以把一部分玩法放进浏览器，让用户不启动本项目的业务服务。这两个问题互相关联，但不是同一个问题：语言统一不等于取消权威状态服务，静态托管也不等于没有运行时服务。

当前 004 的目标包含统一世界时钟、多个自主角色、按兴趣范围激活、可回放事件、模型适配器、观察者审计、跨设备存档和服务端策略。它们需要一个不受浏览器生命周期和客户端篡改影响的权威边界。

## 决定

1. **“纯 TypeScript”不作为当前迁移目标。** 当前正式架构继续采用 TypeScript + PixiJS 前端与 Python FastAPI World Kernel。Node/Pi `legacy-v2` 只保留兼容和回滚用途，不能重新成为世界状态权威。
2. **语言和部署形态分开评估。** 将来可以把 Python Kernel 替换为 Node、Deno 或 Bun 的 TypeScript Kernel，但前提是完整通过同一份事件、能力、可见性、CAS、回放和迁移契约；这属于一次新的后端替换项目，不等于“无服务化”。
3. **允许提供纯 TS 的本地单机模式。** 浏览器使用 IndexedDB、Web Worker 和本地规则 Agent 即可运行已下载的世界、时间表和工具；它适合离线试玩、演示和无模型回退。该模式不提供跨设备同步、多人共享世界、可靠后台推进或服务端模型调用，不产生线上世界的权威事件。
4. **正式世界必须保留服务端权威。** 共享时钟、存档、模型密钥、策略 gate、事件审计、观察者和跨设备恢复继续由 Python Kernel 管理。模型请求不能从浏览器携带服务端密钥直接访问。
5. **“无服务化”不作为正式世界的表述。** 静态前端可以部署到 CDN；使用 Edge Function、BaaS、数据库、队列或远程模型时，系统仍然是服务化，只是减少了自维护服务器。无服务部署必须继续满足同一 Kernel 契约和事件持久化要求。

## 运行模式

| 模式 | 前端 | 权威状态 | 模型 | 适用范围 |
| --- | --- | --- | --- | --- |
| 本地单机 | TypeScript + PixiJS + Web Worker | 浏览器 IndexedDB | 本地规则；可选用户自行提供的本地模型 | 离线试玩、演示、无模型回退 |
| 正式世界 | TypeScript + PixiJS | Python FastAPI World Kernel + Event Store | 服务端 Agent Adapter | 共享世界、跨设备、审计、正式存档 |
| 未来替换 | TypeScript + PixiJS | 通过契约验证的 TS Kernel | 服务端 Adapter | 只有在契约、回放和迁移证据齐全后评估 |

## 约束与验收

- 本地模式的时间只在页面或 Worker 存活时推进；恢复时必须显示离线期间的摘要，不得伪称发生了逐分钟的角色生活。
- 本地模式生成的事件必须带 `executionMode=local`，不能直接上传覆盖正式世界；导入正式世界必须经过迁移校验和新的服务端事件。
- 正式模式仍按 004 的 `WorldClock`、`ActivationLease`、ToolCompiler、观察者和回放规则运行。
- 任何声称“无服务化完成”的验收都必须明确是本地单机模式，不能替代公网 HTTP、跨设备、模型密钥隔离和服务端回放验收。

## 影响

这项决策保留了纯 TS 原型的低门槛，同时避免为了统一语言而重新实现已经落地的 Python 世界内核。后续若要改成 TS 后端，应新增迁移任务和兼容期，先让两套 Kernel 对同一事件样本产生一致回放，再切换默认入口。
