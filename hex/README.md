# 002 原型 · 巫柜夜场

[002 spec](../docs/specs/002-hex-theater/spec.md) 的前端原型，用来验证核心玩法与形态，**不是完成品**。

## 跑起来

```bash
npm run hex:dev
```

构建：`npm run hex:build`，产物在 `dist-hex/`（已 gitignore）。
与 001 的 `npm run dev` / `npm run build` 完全独立，互不影响。

> 素材是临时借用的付费素材，**不要提交进公开仓库**，详见根目录 [CREDITS.md](../CREDITS.md)。

## 核心规则：玩家只能说话

这是本原型与上一版的根本区别，也是整个玩法的支点：

| 玩家能做 | 玩家不能做 |
| --- | --- |
| 打字说出想让它做什么 | ❌ 拖动角色 |
| 在娃娃给出的选项里挑一个 | ❌ 点选人物让它移动 |
| 换房间（说一句"去厨房"） | ❌ 直接摆放道具 |

**房间里的一切动作都由娃娃执行。** 没有拖拽手势，没有角色的点击命中区。

## 一晚的流程

```text
玩家说一句话
  → 娃娃复述理解（"你是想让他今晚开不了口"）
  → 玩家确认（"就这样，动手"）
  → 娃娃执行：让角色走到位置、说话、显现后果
  → 战报
```

扣扳机的始终是玩家，动手的是娃娃。如果玩家说的听不懂，娃娃会反问而不是乱动。

### 娃娃的建议权（HF-17c，已实现）

娃娃是**独立 agent**，与角色调用**并行**发出（所以不增加等待时间）。它有自己的观察：

- 大多数时候它什么都不说（`advice: null`）。每次都说就变啰嗦，玩家会开始无视它。
- 疲惫度高、或玩家在伤害自己时才开口。
- 语气分三档：`warn`（劝你收手）、`note`（提一句观察）、`object`（不同意但照做），
  界面用颜色区分。

**玩家不采纳时**：整场戏照演，但建议被记进它自己的记忆（`declined`），疲惫度 **+1**。
不采纳不是没发生——这是建议有重量的前提。

实测例子（第 9 夜、疲惫度 8）：

> 阿布：你眼睛都直了。B 不难受，是你撑不住了。

注意它把**玩家角色 B** 和**玩家本人**区分开了：戏里挨打的是 B，撑不住的是你。

设计与论证见 [决策 0002](../docs/decisions/0002-agent-split.md)。

## 技术栈

原生 HTML/CSS/JS + **PixiJS 8**（仅渲染）。理解与编排在服务端，见 [server/README.md](../server/README.md)。

```text
前端
  index.html     页面骨架（只有对话，没有游戏控件）
  styles.css     界面样式
  app.js         主流程：对话、改名/请人（都靠说话）、确认、演出 beats
  doll.js        请求服务端并校验返回的剧本
  rooms.js       房间、家具（含 solid 标记）与站位
  stage.js       PixiJS 渲染器：房间、人物、物件反应、天气/灯光叠层
  pathfind.js    BFS 寻路与碰撞（角色绕开实心家具）

服务端
  server/orchestrator.js   六位编排：娃娃+人物并行，环境串在后面，路人本地补位
  server/model.js          模型适配器；娃娃 / 人物 / 环境三种 agent 的调用
  server/local-station.js  无模型时的本地剧本与环境反馈
  server/extras.js         路人 Z（按房间换身份）
  server/rate-limit.js     限流与预算
  shared/cast.js           六个 agent 位、房间、站位（前后端共用）
  shared/environment.js    物件表、身份→动作表、娃娃暗手、canUse()（前后端共用）
  shared/script-contract.js 契约与双层校验（前后端共用）
```

### 六个 agent 位

| 位 | 是 agent 吗 | 舞台上有身体吗 | 可改名 |
| --- | --- | --- | --- |
| 娃娃 && 玩家身体（doll / YOU） | 娃娃是；YOU 不是，它的台词、位置、对物件的动作都由娃娃替玩家给出 | YOU 有 | 娃娃可命名 |
| 环境（ENV） | 是，但**只反馈、无意志** | 没有身体，寄居在物件与天气里 | 否 |
| A / B / C | 各自独立 agent | 有 | **是**（说一句「他叫老张」） |
| Z（路人） | 否，本地模板 | 有，按房间换身份 | 否 |

每个人物**分别调用模型**，各自带着自己的记忆与立场。人物之间并行（总耗时≈单次），
环境串在人物之后再调一次——它得知道谁碰了什么才能有反馈。单个人失败只跳过那个人，戏照演。

### 环境是 agent

房间里的物件、天气、灯光归环境所有。人物对物件做动作（`use`），环境给出可观察的反馈：
一句现象描述（"椅腿蹭着地面吱呀一声"）、可选特效、可选状态变化（天转夜、灯调暗）。

环境**不能**：替人说话、移动人物、推进剧情、发明物件。它是纪录片里的环境音，不是旁白。

谁能对环境做什么，是**性格**而不是权限，全部表驱动（`shared/environment.js`）：

| 身份 | 会做的事 |
| --- | --- |
| 玩家身体 | 坐下、躺下、看窗、关灯、摔手机、看手机 |
| A（villain） | 摔门、踹椅子、按喇叭、锁门 |
| B（rival） | 坐下、续杯、打字、拿杯子 |
| C（witness） | 看、打字、开门 |
| Z（路人） | 按电梯、开水、打字——只做不带情绪的事 |
| 娃娃 | **暗手**：让灯闪、电话响、雨下起来 |

模型给出的 `use` 不在表里就丢弃——契约层硬约束，不靠提示词。实测路人的 `slam door` 被拒，
娃娃的 `flicker lamp` 被放行。

### 寻路与碰撞

角色不会穿过家具。用 BFS 算路径，而不是直线推进——地图只有 18×16 格，BFS 足够快，
也不用维护启发函数。

家具分两类，靠 `rooms.js` 里的 `solid` 标记：

| 类型 | 例子 | 是否挡人 |
| --- | --- | --- |
| `solid: true` | 床、柜、桌椅、灶台、吧台、长椅 | 挡，角色绕行 |
| `solid: false` | 地毯、窗、门、灯具、背景墙 | 不挡，角色可以走过去 |

不区分的话，要么人穿床，要么人卡在地毯外面进不来。

**两个必须处理的边界**（都有自检）：

1. **站位不能落在家具里**，否则角色一出生就被困住。每个房间都要能通过
   「所有站位互相可达」的检查。
2. **目标被占时要退到最近的可达格**，不能返回 null——角色呆立不动看起来像卡死了，
   玩家会以为是 bug。退让时按真实距离排序，不按方环扫描取第一个，否则角色会
   跑到贴墙的角落，看起来像嵌进墙里。

**多人不叠格**：目标格已经有人（或有人正走过去）时，改走它旁边最近的空格。
这条是被物件逼出来的——三个人同时去拿吧台上的酒杯，酒杯只有一个站位，
不处理就叠成一个人。现在他们会围在酒杯周围。

**走位按真实时间算**，不按帧数。PixiJS 把单帧时长钳在 100ms，浏览器降频绘制时
按帧数走位会被饿死（实测 1Hz 的窗格里三个人 13 秒才挪一格）。

**家具布局的一个坑**：酒吧原来的吧台是一整条 16 格宽的实心块，把房间横切成两半，
上半区只剩 32 格可达。改成两段、中间留 x=9 的过道口之后恢复到 182 格。
布置实心家具时要检查它有没有把地图切断。

### 两个会被问到的取舍

**并发 vs 顺序**（`AGENT_MODE`）

| 模式 | 延迟 | 互动感 |
| --- | --- | --- |
| `parallel`（默认） | ≈ 单次调用（实测 3–4.6 秒） | 像同时开口，后说的人听不到前面的话 |
| `sequential` | ≈ 单次 × 人数 | 真实接话，后说的人会回应前面的人 |

默认并发，因为真实模型下单次就要 3 秒，五个人排队要 15 秒以上，玩家等不起。

**动作节流**：一场戏最多一个身体动作。这是契约层的硬限制，不只是提示词约束——
实测模型倾向于给每个角色都加 `shake`，结果所有人都抖一下，等于谁都没抖。

### 模块职责的边界

**接缝在 `shared/script-contract.js`**，不在某个具体文件里。

服务端和前端都校验同一份契约：服务端保证产出合规，前端保证不信任服务端。
这样换模型、换端点风格、甚至换掉整个编排策略，前端的演出代码都不用改——
它只认 beats 的形状。

`shared/cast.js` 是另一个接缝：角色的花名册。模型只能从这里选人，不能发明人物。

## 已知问题

- **家具是用 `Graphics` 画的色块**，不是用图块拼的。房间地板是真的图块，家具与物件不是；
  环境的反馈目前靠文字 + 物件位置的特效表达。
- **并发模式下人物听不到彼此**。默认并发是为了压延迟，代价是互动感打折。
  想换真实接话就设 `AGENT_MODE=sequential`，但延迟会变成单次 × 人数。
- **环境串在人物之后**，一场戏比只有人物时多约一次调用（实测 deepseek-chat 下整场 2–3 秒）。
- **模型回复的人物数不稳定**。同一句话，有时三个人都开口，有时只有一两个。
- **聚合网关的稳定性取决于上游**。实测 `glm-4.5` 返回过 503；同一个模型不同时刻的耗时也可能差一倍。
- **窗口降频时的走位**：已改为按真实毫秒计算，但 RAF 极低频（<1Hz）时仍会一顿一顿。
- 战报不能截图分享（HF-09 只做了一半）。
- 未做真机测试；`prefers-reduced-motion` 只影响部分动画。

## 模型选择

网关挂了 160 个模型。完整对比用 `node --env-file=.env scripts/bench-models.mjs [模型名...]` 跑。

实测（同一段 prompt、三人场景、并发）：

| 模型 | 单次耗时 | 思考量 | 评价 |
| --- | --- | --- | --- |
| `qwen3-max` | **1.1s** | — | 最快，台词稳 |
| `deepseek-chat` | **1.3s** | — | **默认**。速度与质量平衡好 |
| `deepseek-v4-flash` | 2.2s | 460 字 | 快档推理模型，可用 |
| `deepseek-v3.2` | 2.9s | — | 可用 |
| `claude-opus-5` | 3.4s | — | 好，稍慢 |
| `claude-opus-4-8` | 3.5s | — | 好 |
| `gpt-6-astra` | 3.9s | — | 好 |
| `gemini-3.6-flash` | 5.9s | — | 尚可 |
| `kimi-k3` | 10.1s | 1137 字 | 偏慢 |
| `deepseek-v4-pro` | 31.0s | **3365 字** | 太慢：想 3000 多字才吐一句 |
| `glm-5.3` | 32.6s | 4296 字 | 太慢 |
| `gpt-5.6-luna` | 37.0s | — | 太慢 |
| `gemini-2.5-pro` | 13.4s | — | 太慢 |

### 两个坑

**推理模型会吃光 token 预算。** `deepseek-v4-*`、`qwen3.8-max`、`glm-5.3`、`claude-fable-5-1`
这类会先输出一大串 `reasoning_tokens`（实测 460～4296 字）。如果 `max_tokens` 给小了
（比如 256），预算被思考吃光，`content` 就是空的，看起来像"模型没回答"。
本项目已把所有调用的预算提到 2048 以上。

**耗时与思考量正相关。** 唯一的例外是 `gpt-5.6-luna`：不显示思考过程，但依然要 37 秒。

### 想换模型

改 `.env` 的 `MODEL_NAME` 一行，然后重启服务。换完先跑自检确认能调通：

```bash
node --env-file=.env scripts/check-model.mjs
```

想一次对比多个模型，用批量脚本：

```bash
node --env-file=.env scripts/bench-models.mjs
node --env-file=.env scripts/bench-models.mjs deepseek-v4-pro gpt-6-astra
```
